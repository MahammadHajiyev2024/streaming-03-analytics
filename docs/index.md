## Custom Project

### Dataset

The custom project utilizes the core transactional database framework provided in the repository to simulate an active retail checkout monitoring stream. 
* **Name of the dataset file:** The incoming source events are driven from the primary data catalog file `data/sales.csv`.
* **Kind of records:** It contains real-time retail customer transaction records generated point-by-point as buying checkouts take place.
* **Fields included in each record:** Each incoming record includes `order_id`, `timestamp`, `customer_id`, `country_id`, `region_id`, `product_id`, `quantity`, `unit_price`, and `currency_id`.
* **Original or modified dataset:** The structural data format of the original sales dataset was preserved to evaluate real-world production entries against our new edge logic conditions.
* **Reference datasets used:** The application utilizes a localized geography cross-reference mapping file, `data/regions.csv`, to dynamically validate categorical data regions and pull associated regional tax percentage rates (`tax_rate_pct`).

### Data Contract

The pipeline enforces strict data schema rules at the entry point to protect downstream databases from corrupted information.
* **Required fields:** A transaction payload must include valid strings for `order_id`, `customer_id`, `product_id`, `quantity`, `unit_price`, and `region_id`.
* **Optional fields:** Contextual descriptive items like `customer_note` and `discount_code` are treated as optional parameters.
* **Allowed values or reference data:** The record's `region_id` must match a valid, existing entry within the `regions.csv` data lookup map to accurately calculate regional tax variables.
* **What makes a message valid or invalid:** A message is valid if all required keys exist, are structured with the right datatypes, and pass our security filters. A message is marked invalid and instantly rejected if its `quantity` strictly exceeds a maximum reseller cap of 2 units, or if parsing fields exposes abnormal values like a zero or negative quantity or unit price.

### Kafka Messages

The pipeline relies on confluent-kafka to manage streaming communications across decoupled architecture layers.
* **What the producer sends:** The producer reads sequential row dictionaries from the source file, serializes the contents into standard JSON string payload structures, and publishes them to the message broker.
* **Kafka topic used:** All transactional messages are published to and consumed from the core topic: `streaming-03-analytics-case`.
* **Message key used:** The producer writes entries using round-robin cluster distribution across default topic partitions, meaning no explicit message partition keys are bound to the headers.
* **Changes to message fields:** The base message fields remain unchanged on transmission to allow flexible, decoupled processing inside the consumer script.

### Consumer Validation

The custom consumer acts as an inline security screening node right at the edge of our messaging broker connection.
* **Validation checks performed:** The code performs a dual-pass evaluation loop. It first validates structural completeness against required string keys via `validate_required_fields`. It then runs a `try/except` cast to verify that numeric data objects are not corrupted or manipulating checkout limits.
* **What happens when a message is accepted:** When an event is approved, it is enriched with calculated metadata flags, written immediately to a persistent file, and aggregated into our metrics.
* **What happens when a message is rejected or skipped:** When a bulk anomaly or corrupted value triggers a restriction, the consumer generates an explicit terminal alert warning, skips the payload, and steps to the next offset without changing the running totals.
* **How validation protects results:** Edge validation blocks corrupted, negative, or duplicate test entries from passing through to downstream analytical models, ensuring the running calculations remain accurate.

### Data Engineering and Enrichment

Approved payloads are passed to the transformation block to calculate additional business intelligence properties on the fly.
* **Derived fields created:** The pipeline calculates standard properties: `subtotal`, `tax_amount`, and absolute `total`. My specific structural updates enrich each message with two new custom variables: `is_high_value` and `anomaly_status`.
* **Reference data used:** Regional tax rate lists are pulled from `data/regions.csv` to map appropriate pricing modifiers based on geographic origins.
* **Transformation of raw fields:** String values are safely cast to numeric data types, standard tax percentages are applied to the values, and the consumer evaluates the finalized transaction properties.
* **Specific calculation changes:** I added custom conditional checks. If an item's calculated order total strictly exceeds \$100.00, it is enriched with an `is_high_value = True` boolean parameter. In addition, an `anomaly_status = 'APPROVED'` text tag is appended to track successful validations in our logs.

### Streaming Analytics

The consumer avoids slow batch-compilation schedules by continuously updating transactional summaries message-by-message.
* **Values summarized:** The consumer reads and aggregates financial performance from the enriched transaction `total` field.
* **Metrics tracked:** The script tracks four metrics using an active `RunningStats` class instance: cumulative total gross sales, the running average order price, absolute minimum sale size, and absolute maximum sale size.
* **How running statistics changed:** As messages pass validation, the summaries adjust instantly. The consumer logs show these values updating automatically in real time as events flow through the system.

### Experiments

Two clear experimental steps were deployed to change the logic of the baseline script:
* **Phase 4 Technical Modification:** I modified the consumer logic to compute an `is_high_value` true/false flag on transaction values above \$100, adding tailored visual logging brackets (`[MO LOG]` and `[MO ALERT]`) to easily flag high-tier VIP orders visually.
* **Phase 5 Application:** I expanded the data contract by creating a strict operational bulk limit filter that screens and drops orders with a quantity greater than 2 items. I also updated the `initialize_output` function to write these extended headers cleanly into a newly renamed file: `anomaly_detection_mo.csv`.

### Results

* **Production success:** The Kafka producer successfully loaded the source records and published the JSON sequence to the active topic cluster.
* **Consumption success:** The consumer connected to the broker group, read the entries from the beginning of the stream, and successfully applied the custom filtering and evaluation loops.
* **Accepted/Rejected message counts:** Out of 3 streaming messages, 1 message was caught by our reseller filter and successfully rejected, while the remaining 2 valid messages were approved and processed.
* **Output CSV contents:** The script generated a new file named `anomaly_detection_mo.csv` inside `data/output/`. Row 1 contains the complete layout of header columns (including `is_high_value` and `anomaly_status`), followed by the filtered rows showing matching `False` and `APPROVED` attributes.
